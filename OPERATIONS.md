# FOND operating handover

## Release environments and tablet installation

`fond-test.mid-point.co.za` is the isolated UAT environment and `fond.mid-point.co.za` is production. They run the same application code but retain separate databases, orders, sessions and provider configuration. Every successful push to `main` deploys the exact verified revision to staging only. Production promotion is a separate `Promote FOND Production` workflow and requires the full commit SHA; it refuses a revision that has no successful staging deployment.

For staff UAT, open `https://fond-test.mid-point.co.za/staff` before installing. The staging app is named `FOND Staff TEST`, opens directly at `/staff` and carries a persistent TEST banner. After sign-off, uninstall that test app from the operational tablet and install `https://fond.mid-point.co.za/staff`, named `FOND Staff`. Never use the production queue for training or test orders. A production deployment copies application code only; it does not copy staging orders, settings or provider credentials.

## Management

### Availability and trading hours

In **Menu & specials**, each item has an immediate green **Available** / red **Sold out** switch. Sold-out items are removed from customer and manual-order menus, and the server rejects them if an older basket still contains one. Switch back to Available to sell the item again. Existing unavailable items remain unavailable until explicitly switched on.

In **Settings → Trading & fulfilment**, edit Restaurant and Food Truck days separately. Unchecked days are closed. Restaurant opening time and ordinary closing time are editable, with a separate Saturday close. Food Truck has its own opening and closing times and must operate within restaurant hours. Save settings to apply the changes. The approved starting schedule is restaurant Monday–Friday 07:00–18:30 and Saturday 07:00–12:00; Food Truck Monday–Friday 07:00–15:30; both closed Sunday. Times use Africa/Johannesburg. Managed staging and production adopt those days and Saturday close once, preserve the existing weekday times, and retain later administrator edits on restart.

Keep **Enforce trading hours** enabled for these schedules to prevent customer orders outside service hours. Food Truck and mixed baskets follow Food Truck days/hours for both collection and delivery. Saturday restaurant collection slots end at noon; an ASAP basket must also be ready before closing. Staff manual Food Truck intake retains the existing authorised exception while the restaurant is open. Availability and schedule changes are recorded in Change history & rollback.

### Staff tablet sound and notifications

Sound is on by default. A deliberate `Mute sound` choice is saved on that tablet; `Enable sound` turns it back on and plays the test chime. `Test sound` plays the same longer, louder six-tone alert used for new orders. Received orders repeat the chime every 30 seconds until accepted or otherwise moved out of received status, including orders already waiting when the board is opened. Locking the staff board stops the reminder.

Browsers can require a tap after reopening or suspending the app before audio can play. The board automatically tries to restore audio and retries on a normal tap, keyboard interaction or returning to the app. Read the visible status: `Sound on · loud` means the browser audio context is running, while `Sound needs a tap` requires interaction. This cannot detect muted device speakers, Bluetooth routing or insufficient hardware volume. At the start of service, turn the tablet's media volume up, tap `Test sound` and confirm staff can hear it over the kitchen noise.

Tap `Allow notifications` and grant the browser/Android permission once; granted permission is recognised automatically after a reload. Denied permissions must be changed in the tablet's app/browser settings. Android notifications use the service worker and open the staff board when tapped. Notification failures are shown separately and do not stop queue refresh. These are notifications generated by the open staff board, not server push: keep the installed staff app visible, the screen awake and the tablet connected to power/network during service. Closing the app or allowing the OS to suspend it is not supported for dependable new-order alerts. Real tablet speaker volume, Do Not Disturb, Bluetooth routing, screen wake/kiosk settings and a controlled staging-order alert test remain physical-device acceptance checks.

Create a named super admin in Settings using the existing shared admin code. Sign in as that named account and enroll 2FA; once enabled, the shared admin code stops working. Save the one-use recovery codes outside FOND. Managers run operations. Owners can review change history, roll back the latest operational change, and manage staff or manager accounts. Super admins additionally control provider credentials, provider switches, Owner/Super Admin accounts and the shared tablet code. Staff work orders on the tablet. Rotating the shared staff code invalidates old tablet sessions. Trading hours enforcement is enabled on the managed staging and production hosts; collection choices are preferences, not reserved slots.

Menu, trading, website-content and customer-message edits retain before/after versions under Settings → Change history & rollback. Only the latest change to an item is eligible for rollback, preventing an older version from overwriting newer work. Security, provider, customer, payment and retry activity is retained separately without passwords or provider secrets.

The server still needs a one-time `FOND_CREDENTIALS_KEY` (64 random hex characters) for encryption, backed up securely outside Git. Docker/Traefik routing, database volume and `FOND_PUBLIC_URL` also remain deployment configuration. `FOND_ADMIN_CODE` is bootstrap access; `FOND_STAFF_CODE` is an optional bootstrap/fallback until a shared tablet code is saved in Settings. Provider keys, sender, email address and tablet code are changed in the dashboard. Changing or losing the vault key makes saved credentials and authenticator secrets unreadable.

## Optional Yoco checkout activation

Official references reviewed 2026-09-15:
- https://developer.yoco.com/docs/checkout-api
- https://developer.yoco.com/docs/checkout-api/idempotency
- https://developer.yoco.com/guides/online-payments/webhooks/verifying-the-events

Use an isolated staging database for sandbox tests. Configure the vault bootstrap key and `FOND_PUBLIC_URL` on that server; enter the Yoco test secret and webhook signing secret in super-admin Settings. `FOND_ALLOW_TEST_PAYMENTS=true` is only for that isolated staging deployment. Register the Checkout API webhook at https://<host>/api/payments/webhook and enable the Settings switch. Test success, failure, cancellation, lost redirect, duplicate/delayed webhooks and refunds. Check exactly one ledger entry and the staff balance. Secrets remain server-side.

After merchant/domain approval and provider UAT, enter live credentials in production super-admin Settings, keep `FOND_ALLOW_TEST_PAYMENTS=false` and enable the switch. A restaurant-authorized small live payment/refund and payout check is still required before broad release.

The webhook verifies raw-body HMAC, a three-minute timestamp window, checkout ID, amount, currency and mode. Event and payment IDs are deduplicated. Orders enter the staff queue before payment. Started or uncertain checkouts block a second manual receipt. Use Finance checkout IDs to reconcile in Yoco; request redelivery of a missing signed payment notification. Do not take a second payment while the first is uncertain. Uncertain creation older than one hour requires manual reconciliation because Yoco idempotency keys expire after 24 hours.

Cancel/failed return URLs do not prove no payment. Cancelling an order does not refund it automatically. Paid cancelled orders show as refund due. Issue Yoco refunds in Yoco and let the signed refund callback record them; do not manually record the same refund. Manual refund entry is for externally issued refunds without an automatic webhook. Bank settlement, fees and tax invoices remain in the restaurant/accounting system. Yoco Counter order injection, catalogue sync and printer routing are not implemented. Staff must add each accepted FOND order to Yoco Counter manually. Its Yoco reference must be recorded manually or through verified prepaid POS matching before preparation can proceed. Existing pre-migration orders are exempt from that new rule.

## Six-digit staff numbers and Yoco POS matching

Each order has a permanent six-digit staff number, displayed prominently as **FOND 100000** on the tablet. The number is never reset daily or reused, and existing orders receive one once. Customer tracking numbers and secure payment links stay unchanged; a staff number cannot be used for public order lookup. Staff search accepts the six digits. **Copy Yoco note** copies `FOND 100000` for pasting into the Yoco sale note.

For an online-paid order, accept it in FOND, enter its products/modifiers in the restaurant POS, add the exact FOND staff number to the sale note and follow Ray's EFT closing procedure. Do not take another payment. Sandbox-paid orders must only be used with the sandbox. Staff can still record the Yoco reference manually until automatic matching has been connected and accepted.

Super admins connect this under **Settings / Yoco POS reference matching**. Create a personal application for the restaurant's own Yoco business with **business/orders:read** in the Yoco Developer Console. Save its separate business API key in the encrypted FOND vault, select the correct live/sandbox environment and optionally restrict the Yoco location. The online Checkout API secret cannot be used here. **Check Yoco order access** makes a read-only request and shows recent POS order numbers and their payment-method classifications.

Yoco's current API schema describes `other`, not a dedicated manual `eft` method. Compare a known restaurant EFT-closed receipt with that readback before acknowledging EFT mapping and enabling matching. If it does not return as `other`, leave automatic matching off and confirm the actual provider mapping before changing the implementation. Instant EFT is a distinct payment method and is deliberately not treated as an already-paid manual EFT closure. The default is disabled; replacing the business API key disables matching and clears EFT acceptance. POS and online checkout environments must agree.

While the staff board is open, its existing refresh triggers a server-throttled read approximately every 30 seconds. All pages are collected before applying matches (maximum 2,000 results and a 30-day outstanding-order window). Exact single-note matches must have the same ZAR total, zero separate POS tip, confirmed online payment in FOND, a completed POS order, the verified non-card payment mapping, and no refund/return. Duplicate notes, reused POS references, mismatched locations/amounts, unreadable responses and provider errors retain the manual gate and show an issue. A successful match saves the Yoco order ID/reference and an audit event, then unlocks preparation. It never adds a payment record, changes a balance or writes to Yoco. Staff still accept the order and control kitchen/fulfilment stages.

Keep the staff board open and online. This is polling, not background push when the app is closed. The six-digit range provides 900,000 never-reused numbers; exhaustion fails explicitly rather than recycling. Restaurant EFT mapping, physical POS/kitchen printout, exact online-to-POS matching and reporting reconciliation require controlled operational acceptance. Linking references does not itself eliminate duplicate turnover in Yoco or accounting; finance must confirm treatment of the original online payment and separate EFT POS entry before live use.

Official API references reviewed 2026-09-28: [Orders](https://developer.yoco.com/api-reference/yoco-api/orders/list-orders-v-1-orders-get), [personal API keys](https://developer.yoco.com/docs/api/authentication/api-keys), [authentication](https://developer.yoco.com/docs/api/authentication).

## Transactional WhatsApp

Meta Cloud API is the primary production path. In super-admin Settings, save the permanent Meta access token, app secret and a private 24–128 character webhook verification token, then save the phone-number ID, WABA ID, approved accepted/ready template names and template language. Register `https://<host>/api/webhooks/whatsapp` in the Meta app with the same verification token and subscribe to `messages`. FOND verifies Meta's callback challenge and rejects webhook POSTs without a valid `x-hub-signature-256`. The access token, app secret and verification token are encrypted and never displayed again. Meta is preferred whenever configured; Twilio remains a fallback for the already-proven sandbox. Test consenting recipients before enabling transactional WhatsApp. Provider acceptance is not proof of handset delivery.

Opted-in status events persist in a queue processed by staff-tablet polling, so keep the tablet open. Provider acceptance is not delivery confirmation. Missing config and failures appear in Marketing & CMS. Limited retries are available; ambiguous/interrupted sends require checking the provider before retry. No marketing campaigns are sent. Order notification opt-in does not imply marketing consent.

## Customer accounts and emails

Customers can create an account at `/account`; orders placed while signed in appear there. Guest orders remain trackable with their reference. An account email is unverified until its owner confirms a six digit code. Order receipts and accepted/ready/completed emails are sent only for verified signed-in accounts. In Resend, verify `fond.mid-point.co.za` with its required DNS records, then enter the restricted `re_` API key and an `@fond.mid-point.co.za` sender address in super-admin Settings. An unconfigured email provider does not block orders. Email attempts and failed jobs appear in Marketing & CMS, where admins can retry. API acceptance is not inbox delivery proof. [Resend sending domains](https://resend.com/docs/dashboard/domains/introduction), [Email API](https://resend.com/docs/api-reference/emails/send-email).

## Backup and recovery

Deployment creates /app/data/backups/pre-deploy-<timestamp>.sqlite in the persistent volume and stops if backup fails. Monitor disk space and arrange encrypted offsite copies and retention; the app does not automatically delete backups.

For recovery, pause intake and preserve the failed database including WAL/SHM files. Restore a verified backup into a separate volume/path first, run integrity and order/ledger checks against operational records, then switch to the reviewed volume. Never replace an active database. Previous app revisions do not implement new finance/payment behavior; rollback needs reconciliation planning.

Local validation created one synthetic order using the previous image, ran VACUUM INTO, upgraded to the new image, restarted, and started another container against the backup. Order counts and SQLite integrity survived. This is not a production offsite restore drill.

## Customer app promotions

In Marketing & CMS, Add promotion, select Text banner / Image with text overlay / Popup with text / Image-only popup, enter text, optional button category, start/end and Active. Images are required for image cards and image-only popups, and optional for popups with text. Upload JPG, PNG or WebP up to 5 MB. Image-only popups show finished portrait, square or landscape artwork in full, without cropping, darkening or duplicate text; the app supplies a working close button and fits the image within the viewport. Enter the offer and its terms in Image description for screen readers. Tapping the artwork opens the selected menu category; Button text supplies the accessible action label. Artwork does not implement loyalty accrual, redemption or price discounts. For other image formats, use a photo with space for overlay text. Preview, then Save draft or Publish to website. Publication does not alter menu prices or send messages. The app checks schedules on load and refreshes content once per minute while open. If overlapping popups are scheduled, the first active popup wins; at most one popup displays per browser session, outside basket/track/confirmation. A restored browser session may retain the dismissal.

Uploaded images are public by link immediately, even before publishing a draft. They reside in promotion_images in SQLite and are included in database backups. Library limit is 200 images; draft removal does not purge assets, because previous publications may reference them. Any manual archival must preserve image IDs in both current draft and published/previous content. No storage/provider secrets are required.

## App-only coffee rewards

New orders placed while signed in to a verified customer account earn one stamp for each paid Coffee-category item when the order is completed (collected/delivered) and fully paid. Every ten stamps produces a unique one-use code for a subsequent order. Guest, counter/staff and historic orders do not accrue stamps. A redeemed free coffee earns no stamp. Any one Coffee-category item qualifies; the highest-priced base coffee in the basket is discounted, while modifiers/extras and other items remain payable. Codes belong to the recipient's verified email account and only one code applies per order. Codes have no automatic expiry in this version.

Customers see stamps, codes and optional reward-email/SMS preferences in My account. Paste the code into the basket and Apply coffee code; changing the basket requires applying it again. The server checks ownership, price, eligibility and payment environment again on submission. It reserves the code atomically; cancellation releases it, completion consumes it. A zero-total order skips Yoco Checkout entirely and creates no fictitious payment. The staff ticket and email receipt record the actual discount. Staff enter the same discount in Yoco; restaurant acceptance of its zero-value sale procedure is still required.

Super admins can issue an individual gift under Marketing & CMS / Coffee rewards. Enter the recipient account email, a reason and optional email/SMS channels (a mobile number is required for SMS). The recipient can register and verify that email later. Gifts can be revoked only while unused and unreserved. Issuance, reservation, redemption, cancellation, stamp changes, preferences and revocation are audited. There is no bulk campaign sender.

Earned-code delivery requires separate customer opt-in. Email uses the existing Resend configuration; SMS uses the existing Twilio SMS configuration. The staff board and customer rewards page process queued jobs, so keep the staff board open. Missing providers leave jobs pending. Each code/channel is submitted at most once; changing preferences can reactivate pending/cancelled jobs, but accepted or ambiguous sends are never automatically resent. Provider accepted means submission, not inbox/handset proof. Unconfirmed jobs require operator/provider review; no automatic ambiguity resolver is implemented. Codes remain visible in the customer's account even if delivery fails.

Payment environments are isolated: while customer Checkout is sandbox or unavailable, new stamps/gifts/redemptions are TEST only. Moving to live payments does not transfer test balances or codes. Any refund reverses all stamps from that order because item-level refund allocation is not available. Available earned rewards can be revoked; already reserved/redeemed rewards count against future entitlement until purchases cover the deficit. This conservative partial-refund policy needs restaurant acceptance before launch.

Before publishing the promotion or using real rewards, verify a controlled end-to-end earn, email/SMS receipt, one-time redemption, extras, cancellation/refund and discounted/zero-total Yoco entry with the restaurant. Existing live-payment, provider, finance, device, training and backup gates remain open.

## Portrait rewards screen and counter redemption (2026-09-28)

Customers open Coffee rewards in the app header or go to /rewards. This is a separate portrait screen with ten punch spaces, a completed-card FREE state and each available reward's Show code to staff button. The order history remains at /account with a direct rewards link. First-time customers choose Create an account, use their own email and a password of at least eight characters, then Send verification code and Verify email. Staff/admin credentials are separate. The same customer sign-in works on both screens. No account or password was created for the user by this change.

Earning remains app-only. Brett explicitly approved counter redemption: the authenticated staff board now has Redeem coffee, opening the manual order panel on Coffee. Choose the coffee/extras, enter the customer's code, Validate coffee code, add their name/contact and Add to queue. Validation checks availability, verified recipient ownership, current test/live environment and catalogue prices; it does not reserve anything. Order creation repeats those checks and atomically reserves the code with an audited staff actor and the selected items/discount. It attaches the order to the recipient account. No counter items earn stamps, including paid extras or additional coffees in the same basket. Enter the equivalent discount in Yoco, record its unique reference in FOND, then follow the existing preparation/collection steps. Cancellation releases the code; completed collection consumes it. A zero total creates no payment; a positive remainder follows normal counter payment recording. A changed basket/code requires revalidation. Staff must use this flow to validate a displayed code before giving the coffee.

The customer code screen refreshes every 15 seconds and on focus, with a manual Refresh code status button. It hides the large code when its latest state is reserved/redeemed/unavailable or refresh fails. A screenshot is not an authoritative redemption check: the server checks again when staff create the order. No camera access or scanning is implemented. Codes can also still be applied to an app basket. Reward emails/SMS now link to /rewards and explain both redemption paths. Existing promotion publications were not changed in this release. The prior app-only redemption wording is superseded by this section; only earning is restricted to app purchases.

## Customer order-history recovery

The account's latest 100 orders include purchases placed while signed in and guest orders with the exact same receipt email after that account verifies its email. Orders already owned by a different account are excluded, even if their receipt email matches. This is a read-only history lookup: it does not relink ownership, change payments/status or award historic coffee stamps. Name/phone alone is not proof of ownership; orders with another or missing email remain available through their confirmation reference. History refreshes every 15 seconds while the page is visible, on returning to it, and with Refresh orders. A failed read displays an error and retains the last successfully loaded details; it is not an empty history.
