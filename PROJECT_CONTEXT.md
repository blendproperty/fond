## 2026-09-14 — first-party auth and durable order-request store

Provider re-check (gate verification, required before touching src/lib/yoco.ts): searched developer.yoco.com, Yoco's help centre and Yoco's 2026-06-17 "Yoco Next 2026" blog post for any change to the 2026-09-11 finding. Result: no change. developer.yoco.com/api-reference still lists only the read-only Yoco API (fetch orders/payments/payouts) and the Checkout API (create online payment checkouts) — neither accepts a created order for Counter/staff acceptance. The blog's "prep stations" feature is Yoco's own in-house Counter-to-kitchen routing for orders placed inside Counter, not an API for external systems. No printer or order-injection endpoint exists anywhere in the docs, and no partner/marketplace ordering program was found. `src/lib/yoco.ts` therefore still deliberately throws and was not touched. Do not reinterpret this as a green light without a fresh check and a dated source.

Implementation: added first-party email/password authentication (`src/lib/auth.ts` — scrypt password hashing, 30-day session tokens, HttpOnly cookie `fond_session`) and a durable SQLite store (`src/lib/db.ts`, Node's built-in `node:sqlite`, no native module so the Alpine image needs no compiler stage). New routes: `POST /api/auth/signup`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/session`. `POST /api/orders` now requires a signed-in session (401 otherwise) and durably records the requested basket via `src/lib/order-requests.ts` (`GET /api/orders` returns that user's history) — but the HTTP response is unchanged: still `503 ORDERING_NOT_ENABLED`, still no payment taken, no Yoco call, no kitchen order, because the Yoco gate above remains closed. This closes the "no durable order store" and "no authentication" gaps at the infrastructure level without claiming live ordering. The customer-facing UI (`src/components/ordering-app.tsx`) was intentionally left on session-only demo state in this pass — wiring sign-in/sign-up screens and switching the basket flow to the new authenticated endpoints is the next increment, tracked as an open gate below. Dockerfile now creates `/app/data` (owned by the existing non-root `fond` UID 1001) and sets `FOND_DB_PATH=/app/data/fond.sqlite`; `compose.yaml` adds a named `fond-data` volume mounted there so the database survives redeploys; `.env.example` documents `FOND_DB_PATH`.

Testing: `npm run typecheck` passed with no errors. `npm test` — 10/10 unit tests passed (7 previous + 3 new files: `tests/auth.test.ts` signup/login/session/logout including duplicate-email, short-password and wrong-credential rejections; `tests/order-requests.test.ts` records/reads/rejects-invalid-basket/isolates-per-user), all against an in-memory SQLite DB (`FOND_DB_PATH=:memory:`), no state leakage between tests. `npm run build` passed (Next.js production build, all 8 API routes compiled). Manual smoke test against the built standalone server (`node .next/standalone/server.js`, temp `FOND_DB_PATH`): `/api/health` unaffected; unauthenticated `POST /api/orders` → 401; signup → session cookie issued; authenticated `POST /api/orders` → 503 `ORDERING_NOT_ENABLED` with "Your request has been saved"; `GET /api/orders` then returned the persisted request with correct `totalCents` and `blocked_pending_pos_integration` status; `GET /api/auth/session` reflected the signed-in user.
