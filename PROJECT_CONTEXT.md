## 2026-09-14 (later) — CI fix, merge, first VPS deployment, and CI/CD

Implementation: PR #1's CI failed on both `push` and `pull_request` runs. Root cause: `POST /api/orders` had been changed to return `401 AUTH_REQUIRED` for an unauthenticated caller before ever reaching the fail-closed response, but `e2e/ordering.spec.ts`'s "PWA manifest and fail-closed order API" test posts unauthenticated and asserts `503`/`ORDERING_NOT_ENABLED` — a real regression, not a flaky test. Correction to prior API-surface findings (2026-09-11 and 2026-09-14 morning entries above): those findings were wrong about the extent of Yoco's public API and were produced by fetching developer.yoco.com through a single automated tool that was silently missing whole sections of the rendered docs site (it summarized pages down to "only two APIs exist" when the live site's own sidebar lists far more). Re-verified today by driving an actual browser against developer.yoco.com/api-reference and reading its full rendered navigation tree directly. Confirmed real, currently-documented endpoints beyond what was previously found:

- **Catalogue is a real, documented, read-only API** — `GET /v1/items`, `GET /v1/items/:item_id`, plus Item Brands and Item Categories (fetch + list, cursor-paginated, `created_at`/`updated_at` range filters), scope `business/catalogue:read` (deprecated alias `business/products:read`, still accepted). Response includes name, description, `default_price` (amount/currency), barcode, tax, images, variants, modifier groups. **This means FOND's menu can be pulled live from Yoco's own product catalogue** (maintained via the Yoco app or CSV/bulk upload, since there is still no documented *write* endpoint for items/categories/brands) rather than hand-maintained in `src/lib/menu.ts` — a real, buildable win for keeping FOND's displayed menu and prices in sync with what's entered in Yoco. Matching webhook events exist too: Item Created/Updated/Deleted, Item Category Created/Updated/Deleted, so a sync can be push-based rather than polled.
- **Orders API is real but still read-only** — `GET /v1/orders`, `GET /v1/orders/:order_id`; an order has state `open`/`completed`/`cancelled`. Webhook events exist for Order Created/Updated/Completed/Cancelled. This lets FOND *observe* orders that already exist in Yoco's system in real time, but there is still no POST/create endpoint — nothing lets an external system inject a new order with line items for Counter/staff to see. The original core finding stands: **no API exists for FOND to place an order into Yoco Counter or trigger prep-station/kitchen printing.**
- **New: Web POS API** — `POST /v1/webpos` registers a virtual "device" (e.g. a named station), then `POST /v1/webpos/:webpos_device_id/payments` (scopes `business/webpos:read`+`:write`) initiates a **real, in-person card payment on Brett's actual physical Yoco card machine** — the response includes the real terminal model/serial once a physical terminal picks it up, and status resolves to `successful`/`failed`/`pending`. This is a genuine, documented bridge from an external system to Yoco's real payment hardware, distinct from the online-redirect Checkout API. Payload is amount + a free-text `client_reference`/`metadata` only — no line items — and it requires the customer to be physically present to tap/insert a card on that terminal, so it fits an in-store "order on a tablet at the counter, then tap the card machine" flow, not a remote pay-ahead-from-home flow. Not yet evaluated for use in FOND; noted here as a real option for a future in-store ordering flow.
- Also newly confirmed to exist (not yet evaluated for relevance): Locations, Modifier groups, Staff, Card machines (fetch/list existing physical terminals), Capital (merchant cash-advance data), and full OAuth 2.0 token/userinfo/logout endpoints for Yoco Connect-style third-party auth.

Net effect on architecture: the "customer PWA → FOND backend → staff accept → printer" redesign (Yoco used only for payment, FOND owns the order/kitchen state) remains the correct plan — nothing found today changes that core conclusion. What changes: (1) FOND's menu/pricing can now be sourced live from Yoco's real catalogue API instead of hand-maintained, if Brett wants menu management to happen inside the Yoco app; (2) Web POS is a second, real, hardware-integrated payment option worth considering for in-store ordering specifically, alongside Checkout API for remote ordering. Neither changes the still-open finding that no Yoco API can inject an order into Counter or trigger kitchen printing — `src/lib/yoco.ts` remains untouched and still throws.

Process note: going forward, treat any "no such Yoco endpoint exists" conclusion as unverified until confirmed by an actual browser render of developer.yoco.com, not by `WebFetch` alone — `WebFetch` against this specific site has now twice produced confidently wrong negative findings.
