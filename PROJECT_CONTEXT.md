- **Catalogue is a real, documented, read-only API** — `GET /v1/items`, `GET /v1/items/:item_id`, plus Item Brands and Item Categories (fetch + list, cursor-paginated, `created_at`/`updated_at` range filters), scope `business/catalogue:read` (deprecated alias `business/products:read`, still accepted). ## 2026-09-14 (full API surface review) — complete pass over every Yoco endpoint relevant to FOND

Following a direct request to review the entire API reference rather than a sample, every endpoint group in the live sidebar was opened and read (not just listed): OAuth API (introduction, authorize/token/userinfo/logout, token-info), and under the Yoco API — Capital, Card machines, Items/Item Brands/Item Categories, Locations, Modifier groups, Orders (incl. full `Order` schema), Payment Links, Payments, Payouts, Refunds, Staff, Web POS, Webhooks (management + all 12 event-type payloads), plus the Checkout API's Checkouts and Webhook Events sections, plus the `/docs` getting-started and security pages. Findings that materially affect FOND:

- **Authentication model, clarified.** Brett (as the business owner) does not need Yoco's partner/OAuth approval process to use any of the self-serve `business/*` scopes. `developer.yoco.com/docs/getting-started/build-with-yoco/yoco-api/personal-applications` documents a direct path: log in to the Yoco Developer Console, create a "personal application", pick only the scopes needed, generate a static API key immediately (shown once). OAuth 2.0 (Authorization Code flow) exists as a separate mechanism only for third-party apps that need to access *other* merchants' Yoco accounts on their behalf (e.g. a SaaS product serving many independent restaurants) — not needed for FOND acting on Brett's own single business. So catalogue sync, orders/payments visibility, webhooks, and Web POS are all available today with a personal-application API key; only *order injection under an external channel* (the Uber-Eats-style mechanism, see below) requires the separate Partnership application.
- **The full `Order` object confirms the actual mechanism behind Uber-Eats-style integrations.** `GET /v1/orders/:id` returns (among other fields) `channel` (free-form string, Yoco's own example value is literally `"uber_eats"`) and `external_id` (the originating system's own order ID, for reconciliation), plus a full `line_items` array (name, quantity, unit price, modifiers, tax, discounts) and a `payments` array showing each payment's `payment_source` (seen values: `payment_link`; `checkout`, `card_machine`, `webpos` are the other plausible enum members though not enumerated on this page) and `card_machine_id`. This proves external systems can and do inject full itemised orders into a merchant's Yoco account (that's how a Deliveroo/Uber-Eats order appears on Counter and prints) — but `developer.yoco.com/partnerships` confirms this capability is only unlocked via Yoco's formal Partner application + an approved OAuth application, not available through a personal-application API key. This is a real, viable path for FOND, just a business-development one (apply, wait for approval) rather than an immediate technical build.
- **Payment Links may be the practical way to accept real payments today, bypassing the domain-verification block.** `POST /v1/payment_links/` (scopes `business/orders:read`+`:write`) takes just an `amount` and a `customer_reference`/`customer_description` and returns a `pay.yoco.com/r/...` URL with status `pending`/`paid`/`cancelled` — no `successUrl`/`cancelUrl`/redirect domain involved at all, unlike Checkout API. Since the Verified-Domains gate that's currently blocking Checkout API live keys is specifically about a merchant-hosted redirect domain, Payment Links likely don't require it (not yet confirmed with Yoco support — flagged as an assumption to verify before relying on it). If confirmed, FOND could: build the order in its own DB → call this endpoint for the total → send the customer the returned pay.yoco.com link (e.g. via the order confirmation screen or SMS/WhatsApp) → poll or webhook (`payment.created`/order webhooks) to detect payment → release the order to staff. This is a real, buildable stand-in for Checkout API while the domain review is stuck, at the cost of a slightly clunkier customer experience (redirected to a generic Yoco-hosted link page rather than an embedded/branded checkout).
- **Checkout API's own schema supports itemisation for display.** `POST /api/checkouts` (`https://payments.yoco.com/api/checkouts`) accepts optional `lineItems`, `totalDiscount`, `totalTaxAmount`, `subtotalAmount`, `metadata`, `externalId` and `clientReferenceId` alongside the required `amount`/`currency` — so once live keys are unlocked, FOND's actual basket can be shown to the customer on Yoco's payment page and reconciled back via `externalId`, not just a bare total. Also supports an `Idempotency-Key` header to prevent duplicate checkout creation on retry — should be used when FOND eventually wires this up. The `payment.succeeded` webhook payload was also confirmed (nested `payload.metadata.checkoutId`, masked card details) — matches the webhook-verification design already planned.
- **Refunds, Payouts, Payments** are all straightforward read-only ledger data (`business/orders:read` scope covers payments/refunds; each references `staff_id`, `order_id`, `payment_id`) — useful later for a reconciliation/reporting view, not needed for the current build.
- **Staff API** (`business/staff:read`) lists Yoco's own staff records (name, role, active/inactive, staff number) — could be used later to map "who accepted this order in FOND" to a real Yoco staff member for reporting, but FOND's own accept-flow doesn't need this to function.
- **Locations, Modifier groups, Card machines** are read-only reference data (multi-location support, item add-on/modifier definitions matching what `line_items[].modifiers` can carry, and the merchant's registered physical terminals respectively) — none block or unlock anything for FOND's core flow; Modifier groups could be worth syncing alongside Items later if FOND ever needs "add cheese"-style options to match Yoco's own catalogue.
- **Webhook subscriptions are self-serve too** — `POST /v1/webhooks/subscriptions/` (scopes `application/webhooks:read`+`:write`) takes a `notification_url` and a list of event types and returns a signing `secret` shown once, standard HMAC-verification pattern, matching what's already planned for the Checkout API webhook.

Updated recommendation: (1) generate a personal-application API key in Brett's Yoco Developer Console scoped to `business/catalogue:read`, `business/orders:read`, `business/webpos:read`+`:write`, `application/webhooks:read`+`:write` — no approval wait, usable immediately; (2) verify with Yoco support (or by testing in sandbox) whether Payment Links genuinely bypass Verified-Domains, and if so use them as the near-term live-payment path instead of waiting on Checkout API's domain review; (3) submit the Yoco Partnership application in parallel as the real long-term fix for order-injection/kitchen-printing (channel-based orders), while building FOND's own staff-accept-and-print flow now as the thing that works regardless of that application's outcome; (4) still do not touch `src/lib/yoco.ts`'s throwing behaviour until one of these payment paths is actually implemented and tested end-to-end.
