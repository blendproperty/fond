# Functions enquiries and booking calendar

- Public form: `/functions`. Staff calendar: `/hub/functions`, linked from the Hub team workspace.
- An administrator assigns the named `functions` role under FOND Admin > Settings > Team. Existing owner/super-admin oversight is supported. Functions access cannot read Gym/Padel requests or operate FOND orders/admin. Use named-account authenticator setup in the Functions workspace.
- Collects pax, approved cuisine option, preferred date, contact person, email and phone. Company and theme are optional for private functions. Contact/company/theme details are encrypted using the existing vault key. Back up that key with the database according to existing protected backup procedures.
- Every submission is a **pending enquiry**, not a confirmed booking. The current model reserves a whole date, across the single Functions calendar; no room/time-slot or capacity inventory is assumed. Staff must confirm venue/catering/price arrangements with guests separately. A database uniqueness rule prevents two confirmed requests for one date. Cancel/decline releases the date; pending requests do not block it.
- The public calendar returns only confirmed dates, never names, contact details or pending-request counts. Dates are South African calendar dates; past, invalid and more-than-two-year-ahead requests are rejected server-side.
- Staff filter by month/date and set pending/confirmed/declined/cancelled. Status changes do not automatically email guests. Alerts to Michelle use the existing `MIDPOINT_HUB_EMAIL_ENABLED` switch and email provider; they contain a protected workspace link, not enquiry details. Failed alerts preserve requests and are retryable. Real mailbox receipt must be verified separately.
- Named Michelle account provisioning/handover, actual email delivery, staff UAT, retention/privacy owner decisions and capacity/venue rules remain operational gates. No live fixture bookings should be created to test deployment.
